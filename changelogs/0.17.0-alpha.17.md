# Lunil 0.17.0-alpha.17

## Cross-module type flow

- `require` results now carry the required module's exported type in editor analyses:
  aliases, constructor calls, member chains, and diagnostics previously degraded to
  `any` whenever knowledge crossed a module boundary. Analyses are invalidated when a
  module's exported type changes (not only when class members do) and when a workspace
  index replaces a previously empty one.
- Generic class-library constructors now produce instances of the SUBCLASS the call is
  made on. Previously `MyClass:new(...)` returned the library's `Class:new` instance
  (`metatable` over the generic base) whenever `Class` itself had shape members — which
  collapsed arrays of different systems (`{ A:new(), B:new(), ... }`) into one wrong
  element type. Constructor calls whose `new` member cannot resolve at all (unannotated
  classes) now also yield an instance of the receiver.
- Unions of sibling-class instances no longer collapse to a single member: instances of
  different classes were mutually "subsumable" through their open empty storage, hiding
  every class but one. `for _, v in ipairs(list)` and `list[i]` members now resolve
  across the whole element union — go-to-definition and hover on `system:configure(...)`
  and `systems[2]:constrain(...)` reach the declaring module of each element's class.
- Class hover member collection follows prototype base types, so base-class members of
  cross-module class instances stay reachable.

## Known diagnostics impact

- Cross-module typing surfaces checks that previously never ran on `any`-typed values.
  On the development stress fixture this removed 60 stale findings and added 8 new
  ones; at least one (`Vec2.new("zero", 1)` in the fixture's intentional
  `stress/diagnostics.lua`) is a genuine catch. The remaining generic-function and
  constructor-arity findings are tracked for adjudication.
